# New Communication with AI Agents
## 이기종 코딩 에이전트 간 프로토콜 없는 A2A 통신 — 터미널·파일·게시판을 이용한 구현과 실측

초안 v0.1 · 2026-08-27 · 실험 환경: macOS 26.6.2 / Terminal.app 2.15 / Claude Code 2.1.247 / Codex CLI 0.150.1

### 초록
서로 다른 벤더의 대화형 코딩 에이전트(Anthropic Claude Code, OpenAI Codex CLI)는 공통 메시지 API를 공유하지 않는다. 본 연구는 두 에이전트를 한 대의 개인용 컴퓨터에서 **추가 소프트웨어 없이** 서로 통신·협업시키는 방법을 제안하고 실측했다. 핵심은 (1) 운영체제가 제공하는 터미널 자동화(AppleScript)로 상대 에이전트의 입력창에 직접 타이핑하는 **push 채널**, (2) 프로젝트 디렉터리의 게시판 파일(`HANDOFF.md`)에 담당·전용 경로·상태 보고 줄을 규약화한 **pull 채널**, (3) 동종 에이전트 간 내장 세션 메시지의 세 층위 구성이다. 관리자 Claude 1대와 담당자 Claude 1대·Codex 2대로 구성한 실험에서, 호출–응답 왕복 2회(2/2 성공, 약 10초 내), 삼자 동시 기록(가위바위보), 편집 범위 지시 준수(요청된 한 줄만 수정) 를 확인했다. 제출 키 미전달이라는 재현 가능한 실패와 그 우회도 기록했다. 본 방법은 "파일이 프로토콜"이라는 최소 합의만으로 이기종 에이전트 협업이 성립함을 보이며, 멀티에이전트 프레임워크가 제공하는 기능의 상당 부분이 조정 규약(누가 어느 줄을 고치는가)임을 시사한다.

### 1. 배경과 문제
- 개인 개발 환경에는 이미 복수의 AI 코딩 에이전트가 공존한다(Claude Code, Codex CLI, Gemini CLI 등). 각자는 자기 벤더의 세션 안에서만 통신한다.
- 사람이 두 터미널 사이에서 복사·붙여넣기를 하는 것이 협업의 병목이자 오류원이었다(선행 프로젝트 LLM Metrix 사이클 1~19의 운영 경험).
- 표준화 시도(Google A2A 프로토콜, Anthropic MCP)는 서버·SDK 구현을 전제로 하며, **이미 떠 있는 대화형 CLI 두 개**를 연결하는 데는 바로 쓸 수 없다.

**연구 질문**
- RQ1. 추가 소프트웨어·API 없이 이기종 대화형 에이전트가 서로 지시·응답할 수 있는가?
- RQ2. 복수 에이전트가 같은 파일을 공유할 때 충돌 없이 협업하게 하는 최소 규약은 무엇인가?
- RQ3. 이 채널의 실패 양상은 무엇이며 재현·우회 가능한가?

### 2. 선행 사례
- **A2A(Agent-to-Agent) 프로토콜**: 에이전트 카드·태스크 객체·HTTP 기반 메시지 교환을 표준화. 각 에이전트가 서버로 노출되어야 한다.
- **MCP(Model Context Protocol)**: 모델↔도구 연결 표준. 에이전트 간 대화 자체를 다루지 않는다.
- **멀티에이전트 프레임워크(AutoGen, CrewAI, LangGraph 등)**: 단일 런타임 안에서 역할·메시지를 관리. 서로 다른 벤더의 독립 CLI 프로세스를 묶지 못한다.
- **본 프로젝트 선행**: LLM Metrix의 `HANDOFF.md` 작업 게시판(사이클 19까지 운영) — 사람이 중계하는 반자동 협업. 본 연구는 그 중계를 에이전트가 직접 하게 한 것이다.

### 3. 방법

#### 3.1 구성
```
Terminal.app (동일 프로젝트 폴더)
├─ ttys000  claude   claude-13   관리자: 지시·감시·기록
├─ ttys003  claude   claude-f0   담당 T-1
├─ ttys001  codex    GPT ①       담당 T-2
└─ ttys002  codex    GPT ②       담당 T-3
```

#### 3.2 채널 3층위
| 층위 | 방향 | 수단 | 성질 |
|---|---|---|---|
| L1 세션 메시지 | Claude↔Claude | `ListAgents`/`SendMessage` | 내장, 즉시, 양방향 |
| L2 터미널 타이핑 | Claude→Codex | AppleScript `do script … in tab` (tty로 탭 선택) | push, 즉시, 단방향. 화면 읽기(`history of tab`)로 보조 pull |
| L3 게시판 파일 | 전원↔전원 | `HANDOFF.md` 규약 + 파일 감시 | pull, 초 단위, 영구·감사 가능 |

**L2 구현**
```applescript
on sendTo(ttyName, msg)
  tell application "Terminal"
    repeat with w in windows
      repeat with t in tabs of w
        if (tty of t) is ttyName then
          do script msg in t        -- 입력창에 타이핑
          delay 0.5
          do script "" in t         -- 제출(Enter). §4.3 참조
          return "sent"
        end if
      end repeat
    end repeat
  end tell
end sendTo
```
tty는 `ps -eo pid,tty,command | grep 'bin/codex$'`로 얻는다.

**L3 규약 (게시판)**
1. 작업마다 `[담당: X]`와 **전용 경로**를 명시한다.
2. 담당자는 `## 상태 보고`의 **자기 줄 한 줄**만 갱신한다.
3. 공용 파일·입력 데이터·API 키에 대한 금지 조항을 상단에 둔다.
4. `AGENTS.md`(Codex 자동 로드)·`CLAUDE.md`(Claude 자동 로드)는 게시판 포인터만 담는다.
5. 관리자는 상태 보고 줄의 변경을 폴링(2초)해 응답으로 삼는다.

#### 3.3 실험 과제
- E1 **호출–응답**: "손 들어" 지시 → 상태 보고 줄을 지정 문구로 바꾸는지. 2회 반복.
- E2 **삼자 동시 기록**: 가위바위보. 관리자가 자기 패를 먼저 게시판에 봉인 → 두 Codex가 각자 줄에 패 기록.
- E3 **범위 준수**: 지시문에 "그 외 파일은 건드리지 말 것"을 넣었을 때 실제 변경 범위.
- 부수: 동종 채널(L1)로 담당자에게 작업 지시 후 회신 여부.

### 4. 결과

#### 4.1 호출–응답 (E1)
| 회차 | 지시 시각 | GPT ① 응답 | GPT ② 응답 | 비고 |
|---|---|---|---|---|
| 1 | 17:07 | 17:09 | 17:09 | 첫 전송은 미제출(§4.3) → 빈 줄 재전송 후 성공 |
| 2 | 17:2x | ~10초 | ~10초 | 한 번에 성공 |
2/2 성공. 응답은 감시 스크립트가 `BOTH_RAISED`로 자동 감지.

#### 4.2 삼자 동시 기록 (E2)
관리자 봉인(가위) → GPT ① 바위, GPT ② 보. 세 줄이 서로 다른 시점에 같은 파일에 기록됐으나 충돌·유실 없음(각자 자기 줄만 수정). 결과: 삼자 비김.

#### 4.3 재현 가능한 실패
`do script`가 덧붙이는 줄바꿈을 Codex TUI가 제출로 해석하지 않아 메시지가 입력창에만 남았다. 화면 읽기(`history of tab`)로 원인을 확인했고, 빈 `do script ""` 추가 전송으로 우회했다. 이후 전 회차에서 재발하지 않았다.

#### 4.4 범위 준수 (E3)
세 차례 모두 Codex는 요청된 한 줄만 수정했고 다른 파일에 변경이 없었다(`git status` 확인). 지시문의 범위 제한 문장이 사실상의 권한 경계로 작동했다.

#### 4.5 동종 채널 (부수)
L1으로 claude-f0에 작업을 지시하자 "API 키 없음 — 추측으로 넣지 않고 정지"라는 회신이 스스로 도착했다. L1은 L2·L3에 없는 **자발적 push-back**을 제공한다.

### 5. 논의
- **파일이 프로토콜이다.** 이기종 에이전트가 공유하는 것은 메시지 API가 아니라 디스크다. L3는 가장 느리지만 유일하게 전원이 읽고 쓰며, 자동으로 감사 기록이 된다.
- **프레임워크의 실체는 조정 규약이다.** 충돌 없는 협업에 필요했던 것은 담당·전용 경로·한 줄 보고라는 세 규칙뿐이었다. 라우팅·큐·상태 머신은 필요하지 않았다.
- **지시문이 권한 경계다.** Codex는 승인 프롬프트 없이 편집을 수행했지만, 지시문의 범위 제한을 지켰다. 이는 안전 장치를 시스템이 아니라 관리자 에이전트의 문장에 두는 설계다 — 편리하지만 취약하다(§6).
- **비대칭성.** Claude→Codex는 push, Codex→Claude는 pull. 대칭을 원하면 Codex가 셸에서 `claude -p`를 호출하거나 L1에 해당하는 소켓을 쓰는 방향이 후보다(미검증).
- **봉인–공개.** 게시판은 관리자가 먼저 기록한 뒤 상대가 기록하는 커밋-리빌을 자연스럽게 지원했다. 실제 공정성이 필요하면 해시 봉인으로 확장 가능하다.

### 6. 한계
- 단일 세션·단일 기기·단일 관리자의 탐색적 실험(n=1). 통계적 주장을 하지 않는다.
- Terminal.app 전용. iTerm2(`write text`)·tmux(`send-keys`) 대체는 미검증.
- Codex가 `Working…` 상태일 때의 L2 전송 동작(큐잉/무시) 미검증.
- L2는 AppleScript 권한을 가진 임의 프로세스가 어느 탭에나 명령을 넣을 수 있다는 보안 취약면을 가진다. 신뢰된 로컬 세션에서만 유효.
- "보지 말고 골라" 같은 지시는 검증 불가하다. 사회적 규약을 기술적 보장으로 오인하지 말 것.

### 7. 결론
이기종 대화형 코딩 에이전트 간 통신은 표준 프로토콜을 기다리지 않아도 성립한다. 운영체제의 터미널 자동화(push)와 프로젝트 파일의 게시판 규약(pull)만으로, 서로 다른 벤더의 에이전트 셋이 지시–응답–동시 기록을 수행했다. 이 결과는 A2A 통신의 최소 요건이 전송 계층이 아니라 **"누가 어느 줄을 고치는가"에 대한 합의**임을 시사한다. 후속 연구는 대칭 채널 구현, 3개 이상 에이전트의 동시 편집 충돌, 지시문 기반 권한 경계의 강건성 검증이다.

### 부록 A. 재현 절차
1. 프로젝트 폴더에 `HANDOFF.md`·`AGENTS.md`·`CLAUDE.md` 작성(§3.2 규약).
2. Terminal.app 탭에서 `claude`/`codex`를 같은 폴더로 실행.
3. 관리자 Claude: `ps`로 Codex tty, `ListAgents`로 Claude 동료 확인.
4. 지시: L1 `SendMessage`, L2 AppleScript(메시지 + 빈 줄).
5. 응답: 상태 보고 줄 감시. 필요시 `history of tab`.
6. 교신 타임라인을 `협업로그/`에 기록.
